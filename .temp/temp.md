# SDITADC AI 智能调度升级方案：分析与建议

> 整理日期：2026-10-13  
> 评审对象：《SDITADC 项目升级方案：LLM Agent 驱动的多机器人协同调度系统》  
> 本地基准版本：`project/v0.2.1_preview/`  
> 性质：方案评审与建议，不代表新增功能已实现，也不替代用户后续对实施范围的确认。

## 1. 总体判断

方案值得推进。最合理的原则是：**LLM 负责理解自然语言需求和调用工具，任务分配、路径计算、碰撞检查及执行仍由确定性算法完成。**

不过，这份方案对项目起点的描述已经落后于 v0.2。当前已经具有完整取送任务闭环、精确任务匹配、CBS、HTML 独立窗口以及 3D/2D 同步展示。升级应围绕这些能力增量开展，不需要重新从基础 MAPF 实现起步。

最值得新增的三类能力是：

1. 自然语言操作已有调度功能，并根据真实结果反馈。
2. 有明确规则的机器人故障、修复、道路封闭和解封。
3. 固定输入、指标定义清楚的策略对比实验。

## 2. 方案与当前实现的差距

| 方案中的安排 | v0.2 的实际状态 | 建议 |
|---|---|---|
| 先完成任务创建、分配、取送与完成闭环 | 已具备 | 直接复用 |
| CBS 作为后期算法扩展 | 已具备 | 保留，不必退回优先规划 |
| 3D 作为后期可选展示 | 已具备简化 3D、2D 和任务列表 | 保持现状，暂缓美化 |
| 紧急任务到达与升级 | 已有抢占、重新分配和预约接手 | 可作为第一批 AI 工具 |
| 机器人故障、修复 | 尚未实现 | 先定义状态和货物处理规则 |
| 动态封路、解封 | 尚未实现，当前障碍是静态的 | 同步处理地图、距离缓存、路线和展示 |
| LLM 工具调用 | 尚未实现 | 增加独立适配层，复用现有命令队列 |
| 策略对比 | 有基础指标与回放，尚无完整对比流程 | 优先补充基线、事件序列和统一指标 |

当前入口及边界见 [根 README](../README.md) 和 [v0.2 README](../project/v0.2_preview/README.md)。本文基于文档和源码核查，未为这次评审重新运行完整仿真测试。

## 3. 第一批 AI 能力应复用已有功能

建议第一版仅开放以下工具：

- 查询系统状态。
- 查询可用取货点、配送点及名称映射。
- 创建搬运任务。
- 提升任务紧急程度。
- 查询运行指标。

一个足够完整的演示需求是：

> 从取货点 4 搬到 D2，设为紧急，并告诉我由谁接手。

建议执行流程：

```text
自然语言输入
    ↓
查询并确认合法取送点
    ↓
请求创建任务，紧急等级为5
    ↓
后端自动完成任务分配和CBS规划
    ↓
返回任务编号、执行机器人及实际状态
    ↓
模型依据返回数据说明“正在执行”或“等待接手”
```

这已经覆盖“理解需求 → 执行动作 → 获取反馈 → 解释结果”的闭环。先稳定这条链路，再逐步扩大工具范围。

当前地图没有“A区”的正式定义，只有编号作业点。应建立明确的位置别名映射；输入对应多个地点时需要澄清，不能由模型任意猜坐标。

## 4. 工具设计应贴合当前后端

### 4.1 不要拆开已经完整的业务操作

当前新增任务和升级紧急等级后，后端已经自动调度和重规划。因此，不建议要求模型每次分别调用：

```text
create_task → run_scheduler → replan_routes
```

这样会增加重复调用及部分执行的可能。更合适的是一次业务操作返回完整结果，包括任务是否创建、分配结果、规划状态和真实任务阶段。

手动重试规划可保留为明确的异常处理工具，但不应让模型反复调用它来掩盖失败。

### 4.2 复用唯一状态拥有者

现有 `controller.py` 已提供命令队列和状态快照，`server.py` 已提供本地状态与命令接口。接入 LLM 不要求立即换成 FastAPI，也不要求引入 LangChain/LangGraph。

```text
普通UI操作 ───────────┐
                    ├→ 参数及业务校验 → Controller命令队列 → 同一套仿真
LLM工具调用适配层 ───┘
```

模型网络请求应放在独立工作线程中。只有已经校验的业务命令进入仿真队列，不能让模型请求阻塞仿真时钟，也不能维护一份独立的机器人状态。

### 4.3 格式合法不等于业务合法

JSON Schema 等参数约束之外，还需检查：

- **状态过期：** 模型查询后，任务可能已开始装货；执行时要重新检查当前状态。
- **重置后的旧编号：** 利用场景 `generation` 区分不同轮次，防止操作重置后复用的任务ID。
- **重复请求：** 模型或网络重试不能重复创建同一订单，需要请求标识与重复执行保护。
- **操作边界：** 限制工具种类、单轮调用次数、批量任务数量及重试次数。
- **真实结果：** “任务已创建”“已预约机器人”“路径已找到”“搬运已完成”是不同结果，必须分别返回和解释。

仿真时间步变化本身不必让合法下单全部失效；应检查与该操作有关的场景和业务状态，而不是机械要求整个系统快照完全不变。

模型故障、超时、未配置密钥时，普通按钮和仿真主流程仍应正常工作。模型密钥只保存在后端环境变量或未提交的本地配置中。

## 5. 故障与封路是主要工程缺口

### 5.1 工作阶段与故障状态应分开

当前机器人 `phase` 表示前往取货、装货、送货、卸货、停车等阶段，并与任务阶段和载货状态保持一致。

不能只把 `phase` 改成 `fault`。建议单独增加运行状态，例如健康/故障；机器人可以仍处于送货阶段，同时因故障暂停执行。

建议第一版采用明确的处理规则：

| 情况 | 建议处理 |
|---|---|
| 尚未取货时故障 | 原地停止、退出分配候选，任务返回队列 |
| 已载货时故障 | 保留货物及任务归属，挂起；修复后继续 |
| 其他机器人经过故障位置 | 避开其持续占用的位置 |
| 故障恢复 | 根据保留的作业阶段重新规划并恢复执行 |

不应在没有转运规则的情况下，直接把故障机器人的货物转移到另一台机器人身上。货物暂存、交接和转运属于额外功能。

### 5.2 封路必须更新整条链路

当前 `warehouse.py` 缓存了网格最短距离。封路或解封后，需要使相关距离缓存失效，否则任务分配器可能继续使用旧距离。

应统一更新：

```text
地图事件 → 可通行性与距离缓存 → 分配代价与路径 → 3D/2D快照 → 日志与回放
```

第一版应限制封路操作范围：不立即封闭机器人当前所在格，不随意覆盖作业点或停车位。落在占用格的请求可以拒绝，或明确安排延迟生效。

三台机器人规模下，建议先联合重规划三台路线。若仅修改“受影响机器人”，也必须正确保留其他机器人的占用约束，不能忽略它们的预约。

### 5.3 失败原因需要准确表达

方案验收条目中的“无法规划则提示无解”应改为区分：

- 计算预算耗尽。
- 当前搜索时域内未找到方案。
- 取送点确实不可达。
- 等待机器人或路段释放。
- 在明确条件下证明不可行。

一次超时或有限时域搜索失败不等于证明无解。失败后保留现场、说明原因，按规则等待、重试或安全暂停。

## 6. 策略对比应保持目标一致

当前分配已经是“硬优先级 + 本轮精确匹配”。文档中的 `priority_first` 与 `global_efficiency` 并不是清楚对应的两个现有策略。

建议先比较两种方案：

1. 同样硬优先级下的贪心分配。
2. 同样硬优先级下的现有精确匹配。

使用相同的代价定义、任务输入和CBS规划器，先观察匹配方式造成的差异。后续再增加拥堵感知代价。不要同时改变分配和路径算法，然后把效果全部归因于某一项。

### 6.1 固定实验输入

每次对比固定：

- 地图及随机种子。
- 三台机器人初始状态。
- 任务到达序列及紧急升级时间。
- 故障、封路和恢复事件序列。
- 装卸时间、优先级语义及规划预算。

事件按仿真时间步触发，避免LLM API响应速度改变算法实验的输入。对比应该允许真实结果显示取舍，不预设所有指标都一定改善。

### 6.2 先修正指标定义

现有 `avg_wait` 是任务创建到开始装货的时间，包含去取货的路程，不是纯队列等待。建议分别统计：

- 队列等待时间。
- 路上避让等待时间。
- 完整任务周转时间。
- 紧急升级到接手的时间。
- 紧急升级到完成的时间。
- 总移动距离、规划耗时和完成任务数量。

已有任务后来升级为紧急时，需要新增 `urgent_at`，否则紧急响应时间会混入升级前的普通等待。抢占后重新排队，也需要按实际状态累计等待。

CBS搜索中检测出的冲突与执行中发生的碰撞应分别统计。不能把搜索节点数直接称为“避免碰撞数”，也不能仅凭已统计碰撞为0就宣称具备工业级保障。

## 7. AI与算法分别评估

同样的任务、时刻和策略下，增加自然语言入口本身不能证明CBS更优。

| 实验 | 固定条件 | 评价内容 |
|---|---|---|
| 调度算法实验 | 地图、起点、任务与事件序列 | 完成数量、延迟、距离、规划耗时 |
| AI操作实验 | 预先定义的一组自然语言需求 | 意图理解、参数正确率、执行成功率、响应时间 |

如果希望AI进一步参与决策，可以让它依据用户目标在已经验证过的有限策略中选择，再用实验判断选择是否有收益。界面日志应展示工具请求、校验、执行结果和真实状态变化，解释基于返回事实。

## 8. 推荐推进顺序

| 顺序 | 主要内容 | 验收重点 |
|---|---|---|
| 1 | 明确指标，加入贪心与现有匹配的可复现对比 | 相同输入能重跑，指标口径一致，结果如实呈现 |
| 2 | 用查询、创建任务和紧急升级接通自然语言闭环 | 普通UI仍可独立运行；工具结果对应真实状态 |
| 3 | 定义并实现故障、修复、封路和解封 | 任务与货物不丢失，路线和视图同步，失败原因明确 |
| 4 | 按需要扩展机器人数量与策略 | 先解除固定三台假设，再做规模和性能验证 |

文档中的6～10台演示应先改为三台。当前代码、停车终点分配及颜色等仍有固定三台的假设，扩数量不是单独改一个配置值。

现有3D保持简化。暂缓训练拥堵模型、强化学习、多角色Agent、长期自主规划和大框架迁移，优先形成能展示、能复现、能解释的成果。

## 9. 实施前仍需确认

- 模型供应商、工具调用能力、API配置和实际使用预算。
- 故障生效的安全边界，尤其是装卸过程中及载货时的处理。
- 封路操作范围，以及是否支持延迟封闭占用格。
- 策略对比的目标与指标，不把不同目标混称“全局效率”。
- 是否改变原先仅普通预设、固定三台机器人的范围。

文档中的约3人、约20天属于方案假设，不能据此推算当前实际剩余开发时间。
