# AWCS：复杂地图、多机器人及任务—路径联动升级执行方案

编写与检索日期：2026-10-15（Asia/Hong_Kong）。

项目名称：**Agent-Assisted Warehouse Coordination System / 智能仓储协同调度系统**。最终报告题名仍使用：**基于 AI Agent 的智能仓储多机器人协同调度系统**。

**文档状态：待执行方案。此次仅检查源码、检索论文及公开项目、编写文档，没有修改程序、提高数量上限、安装依赖或接入外部求解器。下文的规模、性能和阶段成果均为建议目标，不是已经实现或测试通过的能力。**

## 1. 总体决策

本轮升级应从“三机示例”转向“数量可配置的在线多机器人取送系统”，同时保留现有任务规则、AI工具、双窗口、2D/3D、暂停下单和输入事件回放。

推荐主线：

> 通用地图拓扑分析 → 多项式任务匹配 → 无副作用的任务/路径候选 → 安全时间区间预约 → 局部联合修复 → 有安全边界的滚动规划 → 按需接入原生求解器。

不建议直接把CBS替换成某个GitHub项目后立即提高机器人上限。优先解决分配复杂度、业务约束适配和安全提交，再扩规模。

建议将 **16～32台作为第一轮扩展的正式验收目标，64台作为后续实验目标**；使用1/3/6/12/16/24/32的测试梯度，64台单列实验结果。最终对外支持数量取决于地图、任务流、主机与验收结果，不能把“允许填写64”写成“稳定支持64”。算法与接口按任意N设计，不写死三机组合或按三台枚举。

## 2. 当前实现的事实与瓶颈

以下来自当前 `project/v0.3_preview/` 源码，不是历史方案推断。

| 模块 | 当前实现 | 扩展时需要处理 |
|---|---|---|
| `scheduler.py / exact_matching` | 机器人位掩码动态规划，复杂度含 `2**N`；按等级数量、软偏好、ETA、到达顺序比较 | 不能靠提高上限扩到32/64台；调用它的人工指定校验也必须同步替换 |
| `simulation.py / dispatch` | 紧急接手/未来预约与剩余空闲分配两阶段；普通在途任务一般保留执行者 | 保留两阶段业务语义，避免新算法无意增加自动改派权限 |
| `completion_cost` | 剩余释放时间、静态最短路与装卸时间；不预测多机冲突等待 | 可以增加拥堵估计，但非独立的交互代价不能仍宣称全局线性匹配最优 |
| `planning/astar.py` | 带时间、路点进度及装卸剩余量的A*；支持等待，装卸原子 | 长等待和长时域会产生较多状态；升级SIPP时需保留装卸与已完成路点代价 |
| `planning/cbs.py` | 发现最早顶点/交换边冲突后分支；限制6000个高层展开节点 | 缺少走廊推理、冲突优先选择等；高冲突情况下难扩规模 |
| `planning/prioritized.py` | 尝试若干预约顺序；逐时间步保存顶点、反向边和终点占用 | 内存随时域和机器人增多，顺序变化不能保证找到存在的方案 |
| `ensure_plan` | 初始时域 `max(260,静态路程下界+40)`；CBS失败后重试扩大时域，再预约兜底 | 原样从头重试会丢失计算成果；三机各阶段约2秒预算，更多机器人CBS预算降到0.35秒，并不代表扩展能力提高 |
| 规划与执行检查 | 检查障碍、一步运动、同格和交换边；规划失败安全暂停 | 需要增加服务语义、方案版本、窗口边界及候选归属的一致性检查 |
| 无进展保护 | 有任务且全局无移动/装卸进展12步触发重规划，24步暂停 | 长走廊合理等待可能超过阈值；机器人来回走又可能掩盖活锁 |
| `warehouse.py` | 按目标BFS距离缓存；随机障碍保护端点及邻格并逐次检查全图连通 | 不需要重新“发明距离缓存”；需增加内存边界、拓扑信息和随机生成效率 |
| `map_format.py` | 宽高各≤256；每组点≤64；程序机器人≤12；起点为停车位的相邻前缀 | 数量上限、起点池、停车位及地图容量须一起扩展；连通性不证明多机可解 |
| `optimal_parking` | 匈牙利分配，主要最小化停车距离，停车点唯一 | 缺少对堵塞瓶颈、占据通道及频繁换停车位的考虑 |
| `Controller` | actor是唯一写入者；规划目前同步发生在actor内，读取可继续 | 规划期间命令处理仍会等待；HTTP普通命令等待10秒，不能靠无限延长搜索解决 |
| `BusinessExecutor` | 逐项预检/提交/规划，台账去重；操作生效但规划失败也保留结果 | 异步规划要保持这项语义，不能重复创建或把未规划谎称未创建 |
| 保存与回放 | 保存地图、机器人数量及输入事件；回放不调用LLM | 新旧求解器会产生不同时间线，必须区分输入回放与精确轨迹重现 |
| 发布与渲染 | 约110ms轮询；包含地图/任务/路径，快照深拷贝；3D更新会重建路线对象 | 多机时通信、复制、渲染也可能成为瓶颈，不能只测算法内耗时 |

当前地图上限分别为标准仓库6台、中型仓库8台、MovingAI仓库6台；这些不是升级后的目标。第一步保留既有地图限制，在专门验证的新地图上扩容。

## 3. 问题定义与保证范围

### 3.1 本次继续采用的模型

- 静态不规则栅格，四邻域、整数时间步、单机器人占一格，允许原地等待。
- 在线到达的取货—配送任务，取送顺序固定，装卸期间保持位置与货物归属。
- 单机一个当前任务，最多一个紧急未来接手槽位；不顺便引入多订单车载队列。
- 大语言模型负责用户意图与工具调用；调度、路径和安全由本地模块完成。

这更接近 **MAPD / Lifelong MAPF**，并包含人工指定与业务优先级扩展，不等同于标准的一次性MAPF或TAPF。

### 3.2 必须分开表达的保证

1. **安全性**：在上述离散模型内，提交执行的动作无同格、交换边及服务约束违规。
2. **找到可行方案的能力**：算法在预算内找到多少实例，使用成功率报告。
3. **完备性**：仅在论文假设、图条件和无截断搜索等要求满足时讨论；不能迁移成任意随机地图必解。
4. **最优性**：静态代价下本轮匹配精确最优，与含拥堵的有限候选改进、滚动路径质量，是不同层次。
5. **实时性**：同时报告规划、命令响应、整轮调度和界面延迟；不能只展示最后一次求解器耗时。

临时没有可行路线、预算超时、时域不足、地图拓扑不支持该任务、输入不合法必须分别记录。只有能够给出严格证据的情况才标为“已证明不可行”。

## 5. 技术选型结论

### 5.1 第一条可交付主线

1. 保留现有时空A*与CBS作为基准，以及小规模精确路径模式。
2. 将任务匹配改为**支持字典序目标的多项式二分图匹配**，保留旧DP作为小规模测试预言机。
3. 引入SIPP与压缩预约表，生成包含完整取送/装卸/停车的安全方案。
4. 按实际冲突构建相关机器人集合，局部尝试不同预约顺序、优先关系或CBS修复；每次合并后校验全体路径。
5. 在同样业务约束下，对少量候选分配做路径评估，形成有预算的联动改进。

这条路线优先适配现有业务，先验证到16～32台；如果在目标地图上的成功率或P95耗时不达标，再启用后续原生后端门槛，不能仅放宽验收口径。

### 5.2 第二条扩展主线

在上述安全及业务适配完成后，引入**滚动窗口协调**，并试验MIT许可的LaCAM/libMultiRobotPlanning后端。64台先作为实验档，不宣称任意密集地图实时可解。

不用机器人数量作为唯一切换依据。还要看瓶颈密度、冲突群大小、任务/路线长度、静态下界、剩余总预算和历史超时比例。支持调试参数强制选择模式，以便比较。

### 5.3 为什么不直接选一个“大一统最优算法”

- 大规模、在线插单、硬优先级、人工指定、装卸不可抢占与严格全局最优不能同时作为无条件实时承诺。
- 完整联合分配—路径搜索可用于小规模精确对照，不作为大规模默认内核。
- 主线保留本轮线性代价匹配的精确性；含交互拥堵的联动优化明确为有限预算改进。
- 不引入强化学习训练、LLM逐格寻路或需要云端在线求解的依赖。

## 6. 现有功能适配合同

这些是执行前需要写入回归测试的行为要求，不允许为提高吞吐量悄悄削弱。

| 功能 | 必须保留的行为 | 新算法的适配方式 |
|---|---|---|
| 任务等级 | 5→1的硬分层；提升等级不降级 | 使用相同等级数量向量，不能用普通加权总分让大量低优先任务抵消紧急任务 |
| 紧急接手 | 未装货普通任务可被紧急任务抢占；已装货/装卸先完成必要交付 | 冻结非抢占前缀，保留即时/延迟槽位和释放时间估计 |
| 人工指定 | 一台机器人最多一个未结束人工指定任务；不抢走目标机器人的其他订单；装货前才允许调整 | 作为候选边的硬约束；局部修复和第三方求解器均无权解除 |
| 软偏好 | 各等级分配数量优先，再满足可立即接手机器人的偏好，最后比较ETA | 复用同一策略对象；不能改成“偏好机器人忙碌也一直等它” |
| 普通在途任务 | 当前不会为了平均路程不断自动改派 | 首轮联动只优化待分配/本轮未提交候选；在途迁移仍只由已有紧急抢占或用户命令触发 |
| 装卸保护 | 开始装货后不可取消或改派；装卸期间不能离开站点 | 提交方案前校验连续停留及货物托管，不将它仅当作路径末尾等待 |
| 复制任务 | 新ID/创建时刻，默认继承地点和等级，不继承执行状态/机器人/偏好 | 继续走现有领域命令，调度器只读取新任务 |
| 取消任务 | 仅装货前；列表隐藏，内部记录保留 | 取消后作废相关未来预约和规划版本；不重排ID |
| 暂停下单 | 可创建/更新规划，仍保持用户暂停 | `planning`与用户`paused`分离；AI不获得暂停、种子等调试信息 |
| AI业务工具 | 十类工具及明确指令执行原则 | 工具参数默认兼容；不新增由LLM选择求解器/窗口大小的调试工具 |
| 业务回执 | 已创建不等于已分配，已分配不等于已移动 | 明确“领域操作已生效/路线生成中/路线可用”等回执；不让模型根据阶段虚报移动 |
| 批量操作 | 整批预检、逐项执行；失败保留已生效项、停止后续项；停止回复不回滚已生效操作 | 异步化后逐项等待业务决定点，不把整批一口气提交后宣称仍支持原部分成功语义 |
| 保存/加载 | 本版独立输出，回放不调用上游模型 | 新配置持久化、旧版本入口兼容，并明确回放类型 |

## 7. 多项式分配与任务—路径联动的具体设计

### 7.1 先替换指数级分配，不改变目标

建议保留 `exact_matching(slots,tasks,cost,preference)` 的兼容入口，内部委托新求解器。已有 `validate_assignment` 的两次匹配检查、紧急匹配、普通匹配以及ETA展示都走同一实现。

实现选择：优先在现有匈牙利实现基础上扩展，或采用最小费用流。二者解决的是给定独立边代价的匹配；OR-Tools官方提供这类建模示例 [R14]。是否引入OR-Tools取决于依赖与基准，不因论文使用它就增加强制安装要求。

目标顺序保持：

```text
最大化匹配的5级数量 → 4级 → 3级 → 2级 → 1级
→ 最小化现有定义下的软偏好违背数
→ 最小化本轮ETA和
→ 保留现有到达顺序比较，完全相同时采用确定性ID规则
```

- 加入“本轮不分配”的虚拟槽，不能要求每个任务或每台机器人必配。
- 非法边由可行性掩码排除，不依赖固定`10**6`罚数来模拟所有场景的禁止。
- 可以按逐级优化或由可证明下界/上界构造的整数混合进制编码实现字典序；禁止拍脑袋设置几个大权重。
- Python整数可避免固定精度溢出；若使用原生64位求解器，须检查范围，必要时分阶段求解。
- ETA若含浮点拥堵估计，必须定义量化单位及误差；首轮优先整数时间步。
- 对小规模随机代价矩阵，与旧DP对比完整目标向量；完全同分时只允许声明过的确定性平局选择差异。
- 若做候选任务裁剪，必须证明不影响等级与偏好前缀，或明确标记为近似模式；不能裁剪后继续宣称整个任务池精确最优。

### 7.2 联动不是“往距离里随便加几个惩罚”

将联动分三层，按顺序交付：

**A. 共享可行性。** 统一归属、服务、紧急预约、端点和拓扑约束，先避免分配出明显不能安全执行的候选。

**B. 冻结预约下的ETA估计。** 在已有稳定路线、站点占用和瓶颈预约下估计某机器人接某任务的代价。该估计对当前预约模型有效，不等于多个新任务同时加入后的真实总拥堵。

**C. 有限候选联合评估。** 对匹配基线及同等硬优先级/偏好前缀的少量候选，生成整套路径，比较实际可行性与预测完成时间。采用局部交换、受影响机器人重匹配、增量候选分配等手段，不枚举N台机器人全部排列。

建议首轮每次最多评估4个完整候选，冲突局部邻域最多6台，均服从统一总预算；这些是起始参数，基准后校准。

### 7.3 不同候选如何比较

1. 首先满足合法性、货物托管、人工指定和装卸约束。
2. 保持与基准相同的两阶段规则和等级/软偏好前缀；不能用更少紧急任务换短路线。
3. 在符合前缀的候选中，优先采用已验证可执行的完整方案。
4. 路径结果先比较紧急任务预计交付，再比较本轮交付时间和；停车/空驶与方案稳定性作为后续比较项。
5. 只有有限候选时，结果标注为“候选集内最优/有限预算改进”，不称所有分配和未来插单的全局最优。
6. 若没有同前缀的可执行候选，只能反馈本轮尚未形成安全方案，不能暗自取消任务或解除指定。

不将其他候选“超时”记为“不可行”，也不能因此声称保留下来的候选是数学全局最优。

### 7.4 防止反复改派

保留已经提交的当前任务归属，普通改进主要发生在待分配/未提交候选层。停车目标增加稳定性平局规则，避免小成本差反复改停。

未来若要开放普通装货前的自动迁移，应作为单独功能评估，增加重派次数、最小收益和用户可见说明；它不是本轮默认授权的隐含行为。

## 8. 路径规划升级

### 8.1 SIPP与预约表

新增统一预约接口，支持查询顶点安全区间、反向边冲突、服务点占用、已锁定前缀和最终占位。

- 将连续占用压缩为时间区间，避免为每个终点保存整段逐步占用。
- SIPP状态包含位置、安全区间、路点进度、必要的服务进度和多级代价标签。
- 在相同位置和区间，不能只保留“到达最早”的状态便声称适配完成：不同已完成任务代价或装卸进度可能不能互相支配。
- 同时处理反向边交换；只检查目标格空闲不足以避免迎面交换。
- 服务点必须存在足够长的连续安全窗口；任务完成只在装卸状态机确认后发生。
- 保留BFS距离缓存并增加按地图哈希失效、内存上限与紧凑存储。新地图不沿用旧距离。
- 一开始保持当前“当前任务＋紧急预约任务＋独立停车”的完整路点链，降低切换风险。

### 8.2 局部冲突修复

由路线冲突、共享瓶颈和服务资源构建交互图；在全体有效预约中对小冲突群修复，而不是把不在群里的机器人当作不存在。

优先尝试：改变局部通行顺序 → 预约重新规划 → 小群CBS/走廊推理 → 扩大冲突群 → 安全等待/反馈。

局部CBS的走廊约束必须保留等价可行解；如果暂时采用经验性入口限行，应标记为交通策略，不能继续宣称原CBS完备性或最优性。规划优先级只决定让行顺序，不等于擅自调整任务等级。

### 8.3 滚动规划

RHCR类方法可减少长期规划负担 [R05]，但只在完整路径模式的服务和归属校验通过后进入本阶段。

建议初始研究参数：规划窗口W=32步、执行前缀H=4步；W≥H，并按已进入走廊的退出需求、服务剩余时间和拥堵情况自适应扩大。固定W=32不是对所有迷宫的充分条件。

安全合同：

1. 每次校验全体机器人在将执行前缀中的动作。
2. 窗口边界带明确停止/驻留方案，所有机器人在边界后的持续占用仍需校验。
3. 下一窗口未及时生成时，只执行已认证前缀，耗尽后全体在离散时间边界停止；不盲目延长旧路径。
4. 在当前格点模型内，集体停留可保持碰撞安全，但可能堵路；不能将“能安全停下”称为“无死锁”。
5. 对长走廊尽量规划至可退出或可避让的位置，避免短窗口反复把机器人送入相互封堵状态。
6. 装卸保留连续停留；短窗口不得改变已载货归属或跳过配送。
7. 不把尚未规划的尾部描画为已经确认的安全路线；主界面可区分确认前缀与预估路线。

### 8.4 外部固定目标求解器的适配门槛

原生后端返回的路径必须先通过统一验证器，永远不能直接写回`Robot.path`。

- 单目标求解器不知道业务服务阶段；适配器负责生成合法下一目标及固定服务占用。
- 多个任务可以共享取/送点，但部分求解器要求该批目标唯一；应预约站点和设置真实的等待位置，不能伪造取货完成，不能把重复目标简单删除。
- 令装卸机器人“目标等于当前位置”不代表原生求解器一定不移动它；必须有硬冻结约束或验证并拒绝这类路径。
- LaCAM一类后端的随时改进和标准代价性质不能自动延伸为AWCS紧急优先级及在线任务最优。
- 后端不支持某种锁定/路点约束时，返回`unsupported`并用兼容后端，不降级业务约束。

## 9. 地图生成、拓扑和停车

### 9.1 地图分层检查

- **格式合法性**：原有尺寸、坐标、格子类型、起点与停车位规则。
- **单机可达性**：现有连通性检查；外部数据如含多个分量，拒绝或明确选择并记录转换，不能静默删地图。
- **多机风险诊断**：割点/桥、双连通分量、度为2的狭长通道、死胡同、站点入口与停车对连通性的影响。
- **规划压力验证**：对选定任务样本和数量运行协调规划；通过样本不等于所有未来任务必解。

well-formed端点条件可以作为充分条件检查的参考 [R01]，但不是必须用来拒绝所有复杂地图的必要条件。将“不满足某算法理论条件”和“地图一定无解”区分。

### 9.2 随机生成

生成参数分别控制面积、静态障碍比例、房间/走廊结构、通道宽度、可绕行程度和死胡同比例，记录种子与地图哈希。

保留相邻起点池的现有约定；更大数量时生成足够大的相邻出发区及多个出口，不再把32台塞进原三机起点附近。第一轮不偷偷放宽“所有起点相邻”的业务约定；若后续希望分散部署，再单独扩展配置。

取送点、站点前等待区、停车点分开配置。停车位至少满足机器人数量，并在正式验收地图留出额外可用避让位置；额外数量是布局设计依据，不构成一般可解证明。

当前随机障碍逐个做全图BFS，扩图后可批量生成、分析连通分量、修复并校验，或采用保连通生成方法；所有优化最终仍通过原始格式与安全校验。

### 9.3 停车策略

先排除已证实会造成不允许占用的关键通路位置；其余候选按可达性、瓶颈影响、距离及稳定性比较，仍要求每台机器人最终目标唯一。

停车风险可以软约束或硬约束，但应明确策略来源；增加主通道禁停会改变可行域，不能说它仍与旧距离目标完全等价。停车位不足或无法分配时给出具体诊断，不拿取货点临时冒充停车位。

## 10. actor、规划工作进程与一致性

### 10.1 保持唯一写入者

推荐将CPU规划放入可取消的独立工作进程，而不是让多个线程同时修改Simulation。线程可用于IO，但不能假定Python线程会消除CPU/GIL压力。

```text
用户界面 / AI工具
        ↓ 命令及幂等标识
Controller actor：校验、提交领域操作、发布只读快照
        ↓ 冻结的规划请求
Planner worker：候选分配、路径、评分；不访问真实Simulation
        ↓ Proposal / PlanResult
Controller actor：版本检查、全体校验、原子提交、发布
```

初期在规划期间冻结仿真tick，保持可读取、可处理取消/重置等命令；用户原本的`paused`值不因规划而被改写。滚动模式成熟后，才允许继续执行仍有效的已认证前缀。

### 10.2 请求与结果标识

规划请求至少携带：`run_id`、`scene_generation`、`geometry_revision`、`domain_revision`、`base_tick`、`request_id`、`robot_state_hash`与配置版本。

不能只比较当前用于界面发布的`revision`，也不能只比较`generation`：同场景的取消、升紧急、改派都可能让旧结果失效。通过与规划相关的独立版本进行匹配。

连续命令合并为最新需求，每个场景最多一个活跃规划请求和一个待替换请求；有全局预算、过期丢弃、超时终止和工作进程重启。重置/加载/退出使旧结果无条件失效。

进程侧只读取允许的规划数据，不传API Key、聊天内容、Windows凭据或AI配置。

### 10.3 领域提交与路线提交分开

用户“新增任务”命令一旦通过校验，任务ID和输入事件立即由actor提交；工作进程不能因路径失败让已生效命令消失。

自动分配的候选与搜索过程不修改真实`Task.status/robot_id`。完成方案通过检查后，将归属、预约、停车与路线一致提交。用户人工指定等已经生效的领域约束须保留，规划失败只反馈尚无可执行路线。

### 10.4 AI批量与幂等适配

当前`BusinessExecutor.run`在actor内逐项调用同步规划，不能简单换成后台函数后立即把整批标为成功。

推荐引入actor管理的业务操作状态机：每项校验→领域提交→规划结果决定点→记录回执→决定是否进入下一项；AI工作线程等待Future，actor本身不阻塞等待。

- 维持整批预检与每项执行前再次校验。
- 规划失败沿用现有部分成功与停止后续项规则。
- 相同`operation_id`和参数复用同一在途操作/最终结果，不重新执行；不同参数拒绝。
- 在途台账不能因普通LRU容量淘汰而丢失去重依据。
- 停止回复、场景变化后阻止未开始动作；已提交任务不回滚。
- 对已接收但未完成的HTTP命令，使用可查询操作状态或明确完成Future；不能让请求超时后前端自动重发新增任务。
- `applied`描述领域操作已生效，另有路线结果；不把后台排队称为机器人已开始移动。

## 11. 建议的模块与接口

以下为后续目标结构，不是此次已创建的文件。建议在授权执行后建立独立新版工作目录（例如`project/v0.4_preview/`，版本名届时统一），保留现有v0.3作为基准；不复制`.venv`、输出、缓存、真实配置与凭据。

```text
coordination/
  contracts.py        # 不可变请求、候选、评分、认证路径、状态枚举
  policy.py           # 唯一的资格/优先级/归属/装卸策略
  assignment.py       # 多项式匹配与旧接口适配
  coupling.py         # 有预算的候选分配—路径联动
  coordinator.py      # 后端选择、统一预算和回退
  worker.py           # 工作进程协议、取消与结果隔离
planning/
  astar.py, cbs.py     # 保留基准，逐步改进
  reservations.py    # 区间预约、反向边、端点与服务资源
  sipp.py             # 业务路点适配的安全区间搜索
  repair.py           # 局部冲突群修复
  rolling.py          # 后期窗口与安全前缀
  validation.py      # 全体路径及业务一致性验证
  backends/           # 后期原生求解器可选适配器
map_support/
  topology.py         # 地图拓扑分析，与现有maps数据目录分离
benchmarks/
  manifest.json      # 地图、任务流、种子、来源与验收分组
  runner.py
  compare.py
```

现有`maps/`继续保存地图数据，`map_support/`保存分析代码，避免数据目录与Python包同名导入混淆。上图为职责划分，实施时按已有模块边界适度调整。

核心对象建议包含：

| 对象 | 必要内容 |
|---|---|
| `DispatchSnapshot` | 场景/领域版本、tick、机器人状态、任务规则、冻结承诺、地图与拓扑标识 |
| `AssignmentProposal` | 本轮pairs、即时/延迟槽、前缀目标向量、代价模型、可行性与稳定性说明 |
| `PlanRequest` | 路点链、约束、已有预约、预算、取消令牌、模式及确定性种子 |
| `CertifiedPlan` | 全体机器人路径或前缀、服务停留、边界占用、起止tick、验证与请求版本 |
| `PlanResult` | 状态、候选、耗时/展开量、后端、质量范围和诊断；超时也可携带已验证候选 |

算法只返回数据。状态写入继续集中在Controller/Simulation中，避免UI、LLM、外部二进制各自分配任务。

## 12. 更多机器人的系统适配

### 12.1 数量和地图格式

先通过新匹配与回归测试，再把程序级上限从12提高至经过验证的档位；地图上限仍分别配置，不能所有地图自动变为32。

现有每组点≤64，足以先验证32/64台的起点池；64台若还需要更多独立停车/等待点，就应升级点集限制或地图格式，而不是复用坐标。新增字段必须可选并兼容旧地图；大于64的数量暂不混入首轮交付。

所有机器人遍历、校验、错误信息、命令参数、指标和图例按N生成；保持`R1…RN`稳定编号，不因任务取消或重置中的局部动作重排。

### 12.2 读取和渲染性能

- 地图按哈希/版本缓存，避免两窗口每次轮询重复传大块静态网格。
- 路线按`plan_id`变化更新；3D路线重用BufferGeometry，避免每个快照全部销毁重建。
- 机器人状态卡和任务列表按变化更新；数量增大后仍保持当前界面分区，必要时内部滚动/分页。
- 编号始终显示，颜色只是辅助；扩展当前12色循环时考虑线型和选中强调，不依赖32种颜色辨认。
- 2D渲染继续只处理可见格子和缓存；3D批量材质/几何、标签数量与长路线显示可分级。
- 调度、传输、渲染分别计时，不能用关闭3D后的结果冒充完整桌面性能。
- `frames`当前无限累计；增加可配置采样或流式记录，测长时间内存，保存任务事件与运行轨迹的职责分开。

### 12.3 AI状态查询

十类业务工具继续有效，机器人ID来自当前场景而非固定三项；批量任务上限20不因机器人变多而无故改变。

若32/64台与大量任务导致上下文过大，增加可选过滤/分页字段，保留总数、`has_more`与明确的剩余读取方式，不能静默截断。分页需绑定稳定查询快照并有过期机制，防止翻页混入重置后的同名ID。AI仍不接收完整路线、种子、暂停和内部预算。

## 13. 无进展、死锁风险和恢复

改为分别记录：有意等待、服务停留、预约等待、预算超时、局部阻塞、疑似活锁和确认不可行。

现有“全局12/24步无移动”不能直接扩成所有地图的死锁判据。等待图有环只表示风险；机器人在移动也不代表任务取得进展。

建议联合观察：任务阶段变化、交付完成、承诺区间是否兑现、局部占用历史和重复配置。合理退让可能暂时远离目标，不能仅以距离是否下降判断进展。

恢复顺序：

1. 验证正在等待的是有结束时间的服务/预约。
2. 调整局部通道的通行顺序或让空闲机器人移到安全停车位。
3. 对相关机器人联合修复并扩大时域。
4. 在业务允许的候选中重新匹配尚未提交任务，必要时扩大交互群。
5. 整体预算耗尽后保留安全停止状态与明确原因，允许用户继续处理。

恢复不得自动取消用户任务、降低任务等级、打断装卸、解除人工指定或丢弃货物。连续紧急任务可能让低等级任务饥饿；等待年龄只能先用于同等级平局，若将来要跨等级老化，需作为明确的新策略，不暗改硬优先级。

## 14. 记录、回放与兼容

- 保留现有add/priority/cancel/auto/assignment/copy输入事件含义，回放不请求LLM。
- 若建立新版，`persistence.load`必须显式接受旧0.3；不能仅替换`VERSION`后忘记旧版本白名单。
- 新记录保存地图哈希、求解器/策略版本、配置、种子、匹配代价模型和运行环境摘要，不保存凭据与聊天密钥。
- **输入回放**：恢复地图与业务输入，不承诺新旧求解器产生相同路线或完成时刻。
- **历史时序兼容**：旧事件发生时刻可能与新路径的装卸阶段不同。优先提供旧规划配置兼容模式；出现阶段冲突时报告回放分歧并安全停止，不能强行取消已载货任务来“复现”。
- **严格轨迹重现**：若后续需要，应使用另行定义的已执行动作/承诺记录，并在恢复时校验；不能把保存求解器名字和随机种子当成严格确定性保证。
- 原版输出及用户场景不覆盖；基准统一写隔离目录并使用`--no-save`或明确测试路径。

## 15. 基准、指标与验收

### 15.1 两套基准必须分开

**标准MAPF基准**：MovingAI的空图、随机障碍、房间、迷宫、仓库及单次起终点，用于对比求解器能力。

**AWCS业务基准**：配置正式取送点、相邻起点、停车和任务流，覆盖优先级、装卸、指定/偏好及AI写工具，用于证明项目适配。

MovingAI `.scen`不是仓储任务流，也不自动满足相邻起点与停车条件。转换的点集和地图修订均写清；不能把转换后的业务结果冒充官方标准MAPF成绩。未转换且超过当前尺寸上限的地图只用于独立后端基准，不通过静默裁剪塞入应用。

### 15.2 测试矩阵

| 维度 | 建议覆盖 |
|---|---|
| 机器人数量 | 1、3、6、12、16、24、32；64单列扩展 |
| 地图 | 现有三张；32×32随机、64×64房间/随机、128×128不规则、长走廊及瓶颈图 |
| 障碍和拓扑 | 10/20/30%障碍目标；有环、多割点、长单格通道、死胡同、多个出口 |
| 起点 | 保持相邻大起点池；区分出发区拥挤与地图中部拥堵 |
| 任务 | 固定有限批、持续任务流、同站点热点、跨瓶颈往返、不同到达率 |
| 业务事件 | 紧急插单、人工指定、解除、软偏好、复制、取消、装货临界时刻操作 |
| 并发/失败 | 规划期间升紧急/取消/重置/加载/退出；旧结果回到新场景；后端超时/崩溃/非法路径 |
| 展示 | 仅核心、2D、完整2D+3D双窗口，分别报告 |

先用固定的10个种子做冒烟筛查，再对最终代表性单元使用不少于30个种子；不做所有维度的无意义全笛卡尔积。小有限批运行到完成或声明的上限；持续任务流先1000步，再做代表性10000步耐久测试。算法对比使用同一地图、任务事件与资源预算，并记录差异。

### 15.3 指标

- 安全：碰撞数、服务停留违规、货物归属违规、非法改派/取消、过期方案执行，均必须为0。
- 分配：匹配耗时、目标向量、与旧DP/精确小实例的差异、候选数量、改派次数。
- 路径：首次可行解耗时、P50/P95/最大耗时、完整/窗口解成功率、展开量、兜底比例。
- 业务：任务完成率、紧急任务交付时间、平均周转、订单至装货、吞吐、长期未完成任务分布。
- 系统：命令接收/完成延迟、进程通信、丢弃过期结果次数、CPU/峰值内存、网络快照大小、2D/3D帧率。
- 失败：格式拒绝、拓扑诊断、超时、窗口内无解与后端不支持分别统计，不能从成功率分母中静默剔除。

### 15.4 建议门槛（尚未实测）

| 阶段 | 建议门槛 |
|---|---|
| 正确性 | 既有核心与业务测试通过；小规模匹配目标与旧DP一致；所有执行安全项为0 |
| 1～12台回归 | 原地图功能不退化；同等资源下主要完成率不低于基线，尾延迟不显著恶化 |
| 16～32台常规目标图 | 正式冻结的已知可行回归样例全部通过；广泛随机压力实例完整报告成功率与失败原因，不承诺100% |
| 交互响应 | 参考机上命令接收P95目标≤200ms；已接收与已规划完成分开计时；读取不因CPU规划长期阻塞 |
| 规划延迟 | 常规目标图整轮规划P95目标≤1s，保底总预算初设3s；压力实例独立报告，不靠隐藏超时达标 |
| 展示 | 参考机1600×1000完整界面目标≥30FPS；计算繁忙仍可读到最新已发布状态 |
| 64台实验 | 在大图验证吞吐、失败模式、服务适配与资源；达不到门槛则保持实验标识 |

正式验收前冻结参考机CPU/内存、Python、浏览器/WebView、编译器、地图清单及预算。若门槛冲突或不现实，记录实测原因后修订目标，不能把未达标项删掉。本文没有运行上述基准。

## 16. 分阶段执行与交付

| 阶段 | 主要工作 | 交付与进入下一阶段的条件 |
|---|---|---|
| P0 基线与合同 | 冻结源码/配置哈希，执行旧测试，记录三张图和数量梯度；补齐业务语义合同 | baseline报告、失败样例、同一预算的比较入口；此时不提高12台上限 |
| P1 接口和地图 | 不可变候选/请求/方案；拓扑分析；独立安全验证；新起点池/停车图 | 原有行为兼容；候选搜索不能污染Simulation；地图诊断可解释 |
| P2 分配扩展 | 替换DP为多项式匹配；统一人工指定校验；维护等级、偏好、ETA和平局 | 小规模随机矩阵对照通过；32/64台合成匹配不再指数爆炸；仅此时允许受测数量配置 |
| P3 actor与工作进程 | 取消、版本、预算和原子提交；AI逐项Future/台账适配 | 重置/取消/停止/重复请求/进程崩溃测试通过，领域回执真实 |
| P4 SIPP与局部修复 | 区间预约、服务锁、终点占用；小群CBS/走廊策略；保持完整取送链 | 完整安全方案与执行器一致；对现有预约基线测得收益或明确适用范围 |
| P5 分配—路径联动 | 共享可行性、拥堵估计、有限候选联合评价 | 各业务前缀不退化；热点/瓶颈任务流相对独立分配有量化结果；如无收益不默认启用 |
| P6 多机展示/记录 | 快照、路线更新、状态卡、帧记录与旧场景加载 | 16～32台完整界面验收；旧记录兼容说明与分歧诊断可用 |
| P7 滚动与原生候选 | 窗口安全边界、后端协议；MIT后端Windows验证 | 服务锁/重复目标/失败安全门槛通过后才进入64台实验；不强行集成不支持的后端 |
| P8 综合发布与报告 | 固定任务流、长期测试、许可证清单、启动说明、能力边界 | 可复现报告；独立版本可启动；原版与用户数据保持可用 |

P2与P3完成前，不把“更多台”作为面向用户的已支持能力。P5是受预算约束的联动改进，P7是进一步扩展；阶段顺序可按依赖适度并行工作，但不能跳过安全和业务验收。

建议开关：`legacy_full`保留基准；`scalable_full`为新完整路径模式；`rolling`为后期模式；联动单独设为`off/estimated/candidate`。全部属于本地调试/配置，AI业务工具不改变这些设置。新模式未通过门槛时保留旧模式作为回退。

## 17. 本机环境与依赖策略

本次只读检查发现：

- 当前v0.3虚拟环境为Windows 64位Python 3.14.5。
- `ortools`、`scipy`未安装；现有requirements主要为pywebview、pythonnet、httpx。
- PATH可找到CMake、g++、Ninja；未在PATH找到`cl`。这不等于已经核实完整MSVC安装情况，也不等于MIT/C++项目已可编译。

推荐先用纯Python算法替换和离线基准验证接口，避免第一步同时引入复杂构建。若需要原生后端，先在隔离目录验证一个最小可运行Windows版本，再选择：独立JSON进程协议优先，Python绑定其次。核对当前工具链版本、C++标准、第三方依赖及可分发二进制，进程协议同时限制输入、输出大小及超时。

第三方Python包是否支持本机Python 3.14必须在执行时核对发布轮子和兼容性；不能预设`pip install`一定成功。确需其他Python版本时只建立新版专用环境，不修改旧版或全局安装。不要把现有`.venv`复制成新版运行环境。

## 18. 关键风险、回退与最终口径

| 风险 | 应对 |
|---|---|
| 数量上去了，匹配仍指数级 | P2对所有调用点替换；旧DP只在测试和明确小规模基准中运行 |
| 联动破坏硬优先级或人工指定 | 唯一策略对象、固定前缀、全候选检查和语义回归 |
| 窗口内安全却长期堵死 | 安全边界与进展指标分离、走廊退出、局部恢复、明确实验能力 |
| 原生求解器挪动装卸机器人 | 硬冻结适配及提交前校验；不支持则拒绝/回退 |
| 后台规划使用旧任务或旧场景 | 独立领域版本、tick/状态哈希、过期丢弃和有界取消 |
| 请求超时导致重复任务 | 领域操作台账与在途Future去重；明确已接收/已完成状态 |
| 引入新算法导致旧事件时序不同 | 旧配置兼容、回放分歧诊断，避免强制违反货物规则 |
| 获得短路线却频繁重派/重停 | 已提交归属稳定、未提交层优化、稳定性平局规则 |
| 仅核心快，桌面很慢 | 分开测规划/快照/网络/3D与长时间记录，统一端到端验收 |
| 把开源许可或论文保证误用 | 固定上游版本与许可证；标准MAPF和完整业务分别说明 |

最终报告建议表述：

> 系统在可配置多机器人规模下，结合优先级约束任务匹配、安全路径协调与有限预算联合优化，在给定地图和任务流基准中评估规划成功率、吞吐与响应时间。安全性依据当前离散模型的逐方案与逐步验证；最优性和完备性按具体模块及条件分别说明。

避免表述为“任意不规则地图无死锁”“任意数量实时全局最优”“通过接入LLM获得最优多机路线”。

## 19. 执行时优先落实的清单

1. 新版本保留v0.3基准，保护本地密钥、场景和旧版输出。
2. 统一业务约束；明确人工指定、软偏好、装卸、紧急预约与取消的回归合同。
3. 替换所有指数级匹配调用点，以小规模DP对照证明目标没有暗改。
4. 建立无副作用候选、统一验证器和actor原子提交。
5. 加入可取消规划进程和真实业务回执，处理同场景任务变更及旧结果。
6. 引入SIPP/区间预约与局部修复，再用有限候选实现联动。
7. 在验证过的地图扩到16～32台，同时检查通信、渲染和记录。
8. 滚动窗口与64台后端单列阶段，不用单目标演示替代完整取送适配。
9. 用标准MAPF和AWCS业务两套基准给出结果，保留失败实例与能力边界。
